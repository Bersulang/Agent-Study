## 3. 从问题建立机制

### “多查几个来源”为什么不一定更可靠

问题是“工单应在多少小时内回复”。policy-a说24小时，policy-b说48小时，old-policy说72小时但已经失效。若把三个数字交给模型，让它选最顺口的一句，就丢掉了版本与冲突信息。

本课先把研究分成可检查的步骤：限定来源、去重和控制预算、取出有效资料、按事实字段归并、判断冲突、最后生成报告。检索与写作只是不同职责，默认代码用确定函数和线程池演示，不把线程本身称为自主Agent。

### 预算在并发之前执行

research先用set去掉重复来源，再sorted得到稳定顺序；若没有来源或唯一来源数超过budget，直接拒绝，不启动线程池。这样重复的policy-a不会消耗两次额度，超预算也不会先发出一部分请求后再通知调用者失败。

ThreadPoolExecutor最多两个工作线程。pool.map把retrieve应用到每个来源，返回结果顺序对应输入顺序，不按完成快慢排序。真实网络仍要逐调用设置超时与来源限制，线程数2不等于已经控制所有成本。

### 汇总事实时保留来源，而不是只留最终值

retrieve对过期资料返回None，聚合时排除它。有效证据中的每个事实进入claims：reply_hours下面保存多条value与source记录。`setdefault(key, [])`在键首次出现时放入空列表并返回它，随后append把本条证据加入；已有键则复用原列表。

冲突判断比较同一字段下不同value的数量。24与48同时存在就产生冲突，不能通过“多数投票”或措辞融合凭空得到36。若只有重复转述的24，也只能说明值相同，不证明来源独立或事实真实。

### 报告什么时候允许给确定结论

有claims且无冲突时status=ready，report才格式化事实与来源；有冲突则needs_review；全部来源失效则no_evidence。报告没有擅自选择看起来权威的来源，因为示例根本没提供权威等级与生效版本裁决规则。

Java中可以把并行检索对照受限ExecutorService，把claims对照按字段分组的证据表。拆成多个角色是否有价值，仍要与阶段38的单流程基线比较，不能靠角色数量证明质量。

<details><summary>先预测：只传old-policy会得到ready但报告为空吗？</summary>

不会。retrieve返回None，聚合后claims为空，因此status为no_evidence；report明确不生成确定结论。缺少证据本身就是需要保留的业务状态。

## 5. 跟踪一次完整执行

用源码中的固定来源追踪三次调用：

| 来源输入 | 有效证据 | claims中的reply_hours | 最终状态 |
| --- | --- | --- | --- |
| policy-a | A来源 | 24，来源policy-a | ready，可带引用报告 |
| policy-a、policy-b | A与B来源 | 24与48，保留各自来源 | needs_review |
| old-policy | 无 | 无 | no_evidence |

默认输出的“冲突状态”由结构化比较产生，不是由模型评价文本得出。要排错，应先看retrieve是否返回了过期资料，再看claims是否丢失source，最后看report是否在非ready状态仍给确定数字。

[示例](examples/demo.py)里`if conflicts else ... if claims else ...`是条件表达式。可以按三段普通if理解：有冲突优先待复核；否则有事实才ready；否则无证据。练习需要扩展来源过滤和去重，但不要直接照抄确定性资料作为真实调研结论。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 报告看起来完整却无来源 | 先生成结论再补引用 | 先建证据表再生成报告 |
| 搜索一直继续 | 没有预算和结束条件 | 限制任务数，证据不足时明确结果 |
| 冲突政策被平均 | 把相互矛盾数据直接汇总 | 确认版本与范围，必要时人工核实 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 9. 企业工程边界

换成真实资料后，来源真实性、时效与注入边界仍需检验。多个工作单元使用统一证据契约只是让结果可汇总，不使错误来源自动变成可信来源。

默认研究员是确定性代码，来源是明确标注的教学夹具，不是实时网页或真实企业政策。真实项目替换为搜索工具与模型节点，保留同一证据契约、引用核验、网页注入防护和总预算。

生产接入需要按场景明确身份、数据保留、故障恢复、容量和发布策略。本课程案例的验证范围是本地确定性行为，未调用真实外部模型或声称在生产环境通过。
