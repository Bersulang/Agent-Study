# 阶段 56：企业知识与工单协作助手：毕业交付

[课程首页](../../README.md) · [完整路线](../../docs/roadmap.md) · [本课知识](knowledge.md)

## 1. 业务场景

把前面分散的机制连接起来：用户查询政策，系统并行查看知识与业务；创建工单先形成持久草稿，再以绑定参数的批准执行。重复请求与重启不能导致重复工单。

## 2. 学习目标与前置知识

能沿一条读写请求解释身份、规划、草稿、审批和事务，并在独立项目中验证失败恢复与新需求。

毕业项目沿用[连续主项目里程碑](../../docs/milestones.md)的成果；需要能独立运行阶段39服务、理解审批持久化和权限边界。阶段30—38多Agent模式不是先修，最终可选择单Agent或工作流架构。遇到不理解的语法先回到对应阶段复习。

本课把已有机制组合为一条完整请求路径。验收时需要能解释正常结果、失败前后的状态，以及新需求加入后哪些旧约束仍然成立。

毕业成果是可独立启动的项目，而不是单文件。交付目录由学员维护，至少包含启动说明、需求与架构、配置模板、代码、测试/评估、运行轨迹及部署/恢复文档。具体工程任务和依赖安装见[真实毕业API与交付演练](integrations/README.md)。

## 3. 从问题建立机制

### 把一个请求从入口追到数据库

前面的课程分别教过检索、工具、审批和持久化。毕业项目要回答的是：这些机制接起来以后，任意一步失败，系统还能说清楚已经做过什么、还允许做什么吗？

从“创建工单:登录失败”这个请求开始。服务器先根据token取得真实租户与能力，再交给planner提出计划。默认fixture_plan只是确定性函数，识别已知前缀；换成真实模型时，模型也只能提出answer或draft候选，执行器仍会验证字段与权限。

### 草稿不是已经创建的工单

request收到draft后再检查write能力，确认标题非空且不超限，然后计算租户、动作、标题、版本的摘要。数据库草稿表以tenant+key唯一：同一租户同键同摘要返回原状态，同键不同摘要拒绝。

首次请求只插入pending草稿、到期时间和摘要，ticket为None。这个设计把“用户想做什么”与“已获准产生副作用”分开。前端看到pending必须进入审批流程，不能把它翻译成“创建成功”。

### 批准必须绑定当前动作，不能只绑定一个按钮

approve重新认证approve能力，按认证租户与key查草稿。它校验传入摘要与存储摘要相同，并重新计算当前标题的摘要，以防内容已变。只有状态仍pending且未过期时，才插入tickets并把草稿更新为done。

revise只允许修改待审批草稿，重新计算摘要并更新期限。旧批准携带旧摘要，下一次approve时会失败；不能因为同一个任务名称曾被批准，就放行后来改过的参数。cancel也只把pending草稿改成cancelled，终态不会倒退。

### 数据库事务保证了哪一段

approve把查询、工单插入、草稿完成更新放在一个本地事务内。BEGIN IMMEDIATE提前请求写事务，使竞争审批在本地SQLite边界内序列化；唯一约束进一步防止同租户同键重复创建。closing负责关闭连接，连接的事务上下文负责提交或回滚，两者不可混为一谈。

已经done的请求返回保存的ticket，不再插入新工单。示例重新构造Assistant并连接同一个数据库，验证重新连接后的重放；它不是完整的进程崩溃恢复或容器重启演练。调用外部Spring服务的副作用也不在这个SQLite事务里，必须由业务服务提供幂等与结果查证。

### 只读分支与交付边界

answer并行查询知识和当前租户工单数，每个线程自己建立数据库连接。知识来源目前是限定的教学夹具，没有资料时返回no_evidence，而非补一个看似可信的政策答案。Java Web可以对照Controller→Service→Repository的职责分工，但本教学规模不为了分层而创建大量抽象。

毕业交付还需要真实配置、测试评估、运行说明与恢复证据。单文件基线帮助理解因果链，不能替代独立可启动的项目；是否使用多Agent应由需求与评估收益决定，不以角色数量作为毕业标准。

<details><summary>先预测：草稿pending时改了标题，拿旧digest批准，会新建工单后再报错吗？</summary>

不会。摘要检查在INSERT之前失败，事务里没有新增工单。正确恢复是展示新草稿、获得针对新摘要的批准，而不是忽略摘要错误重试旧请求。
</details>

## 4. 操作演示

默认案例使用 Python 标准库，固定本地数据，无需网络和模型密钥。以下命令从项目根目录运行：

```powershell
.\.venv\Scripts\python.exe .\lessons\56-capstone\examples\demo.py
```

本机示例输出：

```text
知识与业务： answered
创建前： pending

```

先预测结果，再运行；不要只看最后一行，观察成功和失败请求是怎样分流的。

## 5. 跟踪一次完整执行

先按默认演示核对状态，再阅读完整Assistant类：

| 调用 | 数据库变化 | 返回或拒绝 |
| --- | --- | --- |
| 查询政策 | 只读，工单数仍0 | answered，附教学来源 |
| 首次创建请求k1 | 新增A/k1的pending草稿 | pending，ticket=None |
| A批准当前digest | 同事务插入一张工单、草稿改done | done，保存ticket编号 |
| 新建Assistant连接同一库，再批准同摘要 | 不再新增工单 | 返回原done结果 |
| B批准A的k1 | 按B/k1查不到草稿，无写入 | PermissionError |

从[request](examples/demo.py)开始，只跟踪draft分支，先不要同时读所有函数；读懂后再转approve，找到唯一工单INSERT，向前核对身份、摘要、状态和时间。最后跟踪revise与cancel如何使旧路径失效。

`planner=fixture_plan`把函数作为默认依赖，调用`self.planner(question)`才能得到计划；这允许在集成中替换模型而不重写事务。`ThreadPoolExecutor.submit`返回Future，`.result()`取得该工作单元的结果或传播错误。它不是把模型的隐藏推理变成线程。

完整服务、身份和部署验证入口在[integrations](integrations/README.md)。自动练习中的solve只检查离线审批/幂等报告接口，不执行整个毕业项目，不能因该小检查通过就将本课能力标记完成。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 修改参数后仍批准 | 批准只绑定任务名称 | 用参数、租户与版本摘要绑定 |
| 重启重复工单 | 写入结果没有持久化 | 业务唯一约束与幂等键，跨服务另实现查证 |
| 主管扩展权限 | 信任模型提出的工具名 | 执行器白名单与服务端身份校验 |
| 全部示例通过仍不适合生产 | 把有限场景测试当通用保证 | 固定任务和负载下验收，披露未验证环境 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 9. 企业工程边界

毕业验证要加入真实进程重启、失败重试和新需求回归，并披露尚未接通的外部服务。默认输出虽然使用“重启重放”标签，实际只重建对象并连接同一数据库；观察到的范围必须如实说明。

这是可运行毕业参考基线，默认模型与身份均为离线夹具，知识检索是限定关键词；不是已认证的生产系统。真实模型、身份提供方、Java业务、队列和部署按相关章节接入。integrations包含实际FastAPI接口；外部模型和Docker未实调。

生产接入需要按场景明确身份、数据保留、故障恢复、容量和发布策略。本课程案例的验证范围是本地确定性行为，未调用真实外部模型或声称在生产环境通过。
