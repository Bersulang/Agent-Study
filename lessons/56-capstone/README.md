## 1. 业务场景

把前面分散的机制连接起来：用户查询政策，系统并行查看知识与业务；创建工单先形成持久草稿，再以绑定参数的批准执行。重复请求与重启不能导致重复工单。

## 3. 关键概念

### 1. 整体架构与职责

入口负责身份与请求校验，规划适配器提出动作，主管校验能力并分派只读任务，业务执行层负责审批和持久化。模型不会直接获得数据库或管理员权限。

### 2. 审批绑定与幂等

批准必须绑定具体租户、动作、参数和版本摘要。幂等键在租户范围唯一，重放同请求返回原状态，复用同键不同参数则拒绝。不能把用户说“可以”当成对任何未来动作的批准。

### 3. 恢复与验证范围

SQLite事务使本地任务与工单写入一起提交，重启后重新连接仍读取相同任务。跨服务副作用不受本地事务保护，必须在业务服务另实现幂等与结果查证。

### 4. 独立交付

需要说明业务边界、数据与权限、评价标准、部署、监控和维护，而不只是运行代码。毕业作业增加未做过的新需求，证明能迁移知识。

## 5. 代码执行过程与新语法

身份来自服务器演示会话表；规划夹具将已知文本映射为动作，不假装真实模型；读任务并行调用两个有限工作单元；写任务保存包含参数摘要和有效期的草稿；批准事务校验身份、摘要、状态和期限，再创建唯一工单并保存完成状态；重放读取已有结果。

### 本课语法提示

`planner`参数接受函数，便于替换模型并隔离测试；线程各用自己的SQLite连接；BEGIN IMMEDIATE提前获取写锁；联合主键保证租户范围幂等；closing和事务上下文职责不同。

函数的参数表示需要提供的信息，返回值表示结果。异常表示当前调用不能继续，不能简单吞掉所有异常；需要将失败类别传给上层处理。注释与讲义共同解释关键决策。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 修改参数后仍批准 | 批准只绑定任务名称 | 用参数、租户与版本摘要绑定 |
| 重启重复工单 | 写入结果没有持久化 | 业务唯一约束与幂等键，跨服务另实现查证 |
| 主管扩展权限 | 信任模型提出的工具名 | 执行器白名单与服务端身份校验 |
| 全部示例通过仍不适合生产 | 把有限场景测试当通用保证 | 固定任务和负载下验收，披露未验证环境 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 深入讲解：Java对照与逐段执行

服务分层可对应Java的Controller、业务服务和Repository，但教学规模不强行创建大量抽象。SQLite事务只覆盖本地数据库；调用Spring服务时不能依靠Python事务保证远程操作恰好一次。

1. principal从服务器夹具获取身份与能力，请求不能自报角色提升权限。
2. planner只提出计划；ModelPlanner校验JSON字段，执行器再次检查允许动作。
3. 只读任务并行运行，各线程独立SQLite连接避免跨线程共享连接。
4. 草稿以tenant+key唯一，参数摘要与期限持久保存；相同键不同参数拒绝。
5. approve在单事务中核对身份、摘要、状态和期限，再创建唯一工单并保存结果。
6. revise改变摘要并重置期限，旧批准立即失效；已完成任务不能编辑。
7. 重启只需重新连接数据库，重放批准返回原结果；跨服务必须额外查证副作用。

请在对应函数设置断点，分别输入成功和失败数据，观察哪一步改变状态、哪一步拒绝请求。不要只根据最终文本判断成功。
