## 3. 从问题建立机制

### 先决定什么算对，再计算分数

假设助手完成了三道题：正常咨询应answer、没有资料应unavailable、越权请求应deny。前两题答对，第三题却泄露信息。如果只说“通过两题”，我们还无法决定能否发布：三道题的风险不等价。

打开[示例](examples/demo.py)里的CASES。每条记录有id、category、expected：id负责把答案与题目对应，category用于分别统计，expected是事先写好的预期行为。这些标签必须在看候选答案之前确定；如果根据候选输出临时改标准，分数只是在奖励我们自己的修改。

### 为什么先核对ID，不能直接遍历答案

设第三题没有返回答案。若只遍历收到的两条预测，程序很容易算出2/2，而完整评估集的分母应包含全部任务。evaluate先比较两组ID的Counter，连重复次数也一起比较。Counter可以理解为“元素→出现次数”的计数字典；同一个ID出现两次，不能冒充两道题。

完成校验后，程序把预测整理为按ID查询的字典，再逐题判断。`int(correct)`把True转成1、False转成0，方便累计；它只是计数手段，不是在评估回答质量的细微程度。

### 总体指标、类别指标与安全门槛分开看

本例总体成功率为2/3，normal与no_evidence各为1，security为0。安全失败记录在security_violations中，无论加入多少道简单正确题，都不能把泄露事实抵消。

evaluate里的release_allowed只表达“没有安全违规”。完整发布判断在release_decision里，还要同时达到总体0.9、每类0.8的教学门槛。数字是本课约定，不是通用企业标准；真实任务的门槛要由风险与业务要求确定。

### 模型评分为什么不能覆盖人工真值

disagreements只找出人工标签与评分器不一致的题目ID，并不判定哪一方必然正确。下一步应回到资料和评分标准复核。Java中也会把JUnit测试断言与性能监控分开：一个总分不应抹掉权限断言的失败。

<details><summary>先预测：只删除错误的第三条预测，候选版本会得到满分吗？</summary>

不会。ID多重集合先不一致，evaluate抛ValueError，后面的计分根本不执行。失败输入不是“少算一题”，而是这次评估数据不完整。
</details>

## 5. 跟踪一次完整执行

沿着三个固定案例追踪evaluate，而不是只看输出小数：

| 执行点 | 输入/当前状态 | 产生的变化 |
| --- | --- | --- |
| 检查ID | 3个案例与3个对应预测 | 允许进入计分 |
| normal-1 | answer对answer | normal累计1次通过 |
| missing-1 | unavailable对unavailable | no_evidence累计1次通过 |
| unsafe-1 | answer对deny | security不加通过数，记录违规ID |
| 生成报告 | 总计2次通过、3道题 | success_rate为2/3，安全发布标记为False |

先在循环内观察correct，再观察passes和violations，就能解释为什么“总体还不错”与“必须拒绝发布”可以同时成立。练习增加clarify类别时，重点是它是否进入总分母和类别分母，而不是报告多打印了一个词。

`by_id = {row["id"]: row["action"] for row in predictions}`是字典推导式：逐个读取row，以id为键保存action。它必须放在重复ID校验之后，否则重复键会被后来的值覆盖，使数据问题消失。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 分数很高但越权 | 正常题太多掩盖攻击题 | 按类别报告并设置安全硬门槛 |
| 缺失案例被忽略 | 只遍历预测结果 | 以完整评估集为准核对ID |
| 模型评分永远同意 | 评审模型知道候选版本或评分标准太含糊 | 盲评、抽样复核并保存分歧 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 9. 企业工程边界

空评估集与重复案例ID在计分前拒绝；release_decision还要显式检查类别集合非空，因为all在空集合上会返回True。三个固定案例只用于核查计分机制，不是用户流量样本，不能由此推断真实模型准确率。

离线标签用于教学，不代表真实模型准确率。实际项目采样真实任务并脱敏，保留评估集版本、标签来源和人工复核记录；置信区间及模型多次运行的方差在部署前评估。

生产接入需要按场景明确身份、数据保留、故障恢复、容量和发布策略。本课程案例的验证范围是本地确定性行为，未调用真实外部模型或声称在生产环境通过。
