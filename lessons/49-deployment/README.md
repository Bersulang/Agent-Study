服务启动不代表能接工单：数据库不可用时应停止接收新任务，普通进程探活仍可正常。我们先学习配置校验与不同健康状态，再提供实际容器文件。

## 3. 从问题建立机制

### 程序启动了，为什么还不能接流量

设服务进程已经运行，但用于保存任务的目录不可写。若现在接收创建请求，用户可能先收到成功提示，稍后才发现任务丢了。因此部署不是“执行启动命令”一个动作，而是先确认配置与资源满足运行前提，再让流量进入。

load_config先把PORT文本转成整数，并验证1—65535范围。环境变量读出来是字符串，`"8080"`不能不经转换就当作端口数值。DATA_DIR则转换成Path对象，这一步只描述位置，并没有证明目录存在或可写。

### 解析配置与验证运行资源分两步

startup_config进一步检查目录存在、确实是目录，再尝试在里面创建、写入、关闭一个临时文件。它不默默创建缺失目录，因为拼错路径也可能得到一个空目录，让错误看起来像启动成功。

在Windows上，简单权限查询不一定代表最终ACL和实际写入结果，所以本示例选择真正做一次小范围写入探测。临时文件由上下文管理器收尾，不使用业务文件测试，避免覆盖已有数据。

### 存活与就绪回答不同问题

liveness回答“进程是否还在正常运作”，readiness回答“现在是否适合接业务流量”。数据库暂不可用时，进程可能仍活着，存活200而就绪503是合理状态。若把两个探针都设成依赖健康检查，依赖故障可能引发无意义的反复重启。

本地health函数只生成这两个结果，不监听HTTP端口，也没有部署容器。可以与Spring Boot健康端点建立联系，但把结果变成真实探针、配置服务发现与流量摘除，是后面的集成操作。

<details><summary>先预测：PORT="70000"而数据目录也不存在，会先报告哪一个错误？</summary>

startup_config首先调用load_config，所以端口范围校验先失败。目录检查尚未发生。排查应按实际控制流逐层修复，而不是把所有异常统称部署失败。
</details>

## 5. 跟踪一次完整执行

从[示例](examples/demo.py)的load_config、startup_config、health三个函数分别追踪，避免把它们误认为同一个调用：

| 检查 | 输入 | 结果及下一步 |
| --- | --- | --- |
| 配置解析 | 空字典 | 得到默认端口8080及路径对象；不读写目录 |
| 配置解析 | PORT=70000 | ValueError，不进入资源验证 |
| 启动资源验证 | 已存在且可写目录 | 实际写临时文件后关闭，返回配置 |
| 探针结果 | dependency_ready=False | live=200，ready=503 |

默认demo只运行load_config和health，因此输出端口8080并不能证明实际目录可写。要确认启动检查，需要运行本课测试或按练习用临时目录调用startup_config。Java配置绑定同样可能成功，但磁盘、连接和凭证等运行前提仍要另查。

`raise ... from error`保留底层失败原因的关联，同时给调用者一个有业务意义的异常类别。不要在服务启动代码中捕获后继续监听端口，否则前面的拒绝条件就失去了作用。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 程序启动但不可用 | 只检查进程存在 | 增加依赖就绪检查 |
| 重启丢任务 | 数据库保存在容器临时文件系统 | 使用持久卷并验证恢复 |
| 构建把密钥带进去 | 构建上下文包括.env | 最小上下文与.dockerignore |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 9. 企业工程边界

进入集成演练时，再阅读本课的HTTP服务与容器配置：持久数据应写入挂载卷，容器可写层不能代替恢复设计。Compose移除命名卷会删除其数据，不能拿删除卷操作验证“重启后仍保留”。当前讲义不把Docker配置文件存在当作实际部署通过。

本机未发现Docker，因此默认行为实测，容器配置仅提供可执行文件和命令，运行验证留给有Docker的环境。生产基础镜像固定digest、漏洞扫描、权限和资源配置需按部署平台补充。

生产接入需要按场景明确身份、数据保留、故障恢复、容量和发布策略。本课程案例的验证范围是本地确定性行为，未调用真实外部模型或声称在生产环境通过。
