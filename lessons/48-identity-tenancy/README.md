两个企业的工单编号都叫T-001，不能用编号作为唯一缓存键。用户在请求里写tenant=别人公司，也不能改变服务端认证出的身份。

## 3. 关键概念

### 1. 认证与授权

认证回答你是谁，授权回答能做什么。服务端验证后的主体称Principal，权限来自服务器状态，不信任模型提供的角色。真实系统使用验证签名和有效期的凭证。

### 2. 租户范围与资源归属

数据库、检索、缓存、记忆都需要租户范围。资源读取使用tenant和resource_id联合查询，不先取出所有租户数据再让模型挑选。

### 3. 审计与最小权限

最小权限只授予当前任务所需动作，子Agent也不能获得额外权限。审计记录身份、动作、资源、结果，不必记录业务全文。访问被拒绝同样要留痕。

## 5. 代码执行过程与新语法

从服务器维护的演示会话表查身份；请求tenant只能作为需验证的提示，不能覆盖身份；查询用(tenant,id)复合键；每个调用写审计事件，缓存键也包含tenant。

### 本课语法提示

元组可作为字典键，例如(tenant,id)；集合保存角色；字典查找与缓存写入属于服务端机制，不需要交给模型决定。

函数的参数表示需要提供的信息，返回值表示结果。异常表示当前调用不能继续，不能简单吞掉所有异常；需要将失败类别传给上层处理。注释与讲义共同解释关键决策。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 串租户缓存 | 只用工单ID做key | key必须包含认证主体的tenant |
| 请求角色提升权限 | 相信JSON中的role | 角色来自认证后的服务端身份 |
| 代理权限扩大 | 给子Agent管理员凭证 | 委派权限取父任务与工具需求的交集 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 源码分段追踪与Java对照

### 输入和初始化

SESSIONS是服务端离线身份夹具，客户端只提交会话标识。

authenticate返回服务端tenant和roles，不能相信请求自报的角色。

session-a具有reader和writer；session-b只有reader。

TICKETS键是(tenant,ticket_id)，相同编号可以属于不同租户。

read_ticket先认证再比较请求租户，失败不读取缓存。

### 校验与状态推进

cache使用同样复合键，不能只按T-001缓存。

audit只保存用户、租户、动作、资源标识及allowed，不保存工单正文。

write_ticket是新增写接口，写入对象由调用方显式提供以便验证状态。

action绑定tenant、ticket_id与目标state三个字段。

approval必须来自可信审批存储，示例直接构造字典只是离线夹具。

客户端传approved=True不能满足字典动作绑定。

拥有writer只表示角色有资格申请写入，不表示每个具体动作都批准。

即使有匹配业务审批，session-b缺writer仍拒绝。

### 失败与验证证据

越租户请求先拒绝，不能用A租户角色操作B租户资源。

全部权限与审批条件满足后，再检查状态是否open或done。

目标工单不存在则报错，不把更新隐式变成创建。

tickets[key]=state是唯一业务变更点，位于全部校验之后。

失败案例先复制tickets，再确认异常后状态完全不变。

完整审批还需要期限、撤销和幂等记录，本课不重复实现阶段43。

JWT解码只是读取声明，生产必须验证签名、签发方、受众与过期时间。

### Java Web迁移

writer角色对应Spring Security权限，审批记录对应业务层审批实体；两者都需满足。Java Controller不能信任请求tenant，Python服务同样必须从认证身份取租户。复合缓存键相当于tenant与ID组成的record。
