## 迁移练习：由工具观测决定下一步

在独立的[`feedback_practice.py`](feedback_practice.py)中实现`solve_feedback(ticket, owners, max_steps=5)`。`ticket`含`id`和`status`；`owners`将工单id映射到负责人名字。模型替身接收消息历史：它先查询工单，再根据工单观测决定查询负责人或直接结束；最终文本来自工具观测。由你定义并说明消息结构。结果可以是字典，也可以是带`answer`、`reason`、`trace`属性的对象。

至少覆盖开放/关闭两种工单结果，并证明轨迹分别为查询工单→查询负责人、查询工单→结束；同时覆盖工具失败后的受控最终结果和步数预算停止。错误结果不能伪装成成功。只使用只读模拟工具，不实现真实模型或写入业务系统。

基础动作列表练习继续使用[`practice.py`](practice.py)的`solve(data)`契约；反馈循环是第二个独立骨架，不复用或改写基础函数签名。自动校验会分别运行这两个练习，不会用示例动作列表替代反馈循环。此处反馈是离线闭环控制机制，不证明真实模型的工具选择质量。先写输入/输出示例和失败行为，再实现循环；两个练习完成并自测后，再看solutions下对应参考答案。

## 业务需求

实现solve(data)：data为动作列表，支持只读search和final，最多3步，未知工具直接停止；返回trace与reason。search接收query且不得空白；final不能为空。解释一步是否包含最终回答。

## 工作顺序

1. 写出输入、输出、拒绝条件和状态变化。
2. 先列成功、边界、失败三类案例及预期。
3. 实现后从项目根目录运行`.\.venv\Scripts\python.exe tools/check_exercise.py 13`；自动校验日志会分别保存两个练习的结果。
4. 加入调用solve的代码，展示案例结果；当前骨架只报告待实现状态。
5. 解释每个分支为何存在，并保留原始输入以检查是否意外修改。

## 验收

- 第一节完成动作列表执行器的`solve(data)`行为。
- 第二节完成反馈循环的`solve_feedback(ticket, owners, max_steps=5)`行为。
- 至少一个正常案例、一个空/缺失案例、一个失败案例。
- 能指出异常或拒绝发生在哪一层，不能把失败打印成成功。
- 能现场改变一个输入并预测结果，然后实际验证。
- 完成后才阅读 [参考答案](../solutions/solution.py)，说明与你实现的差别。
- 反馈循环完成后才阅读[反馈练习参考答案](../solutions/feedback_solution.py)，分别解释开放/关闭状态如何改变实际工具轨迹。

材料运行通过不代表学员能力通过；验收由实际讲解与修改证据决定。


## 自动练习校验

从项目根目录运行：`.\.venv\Scripts\python.exe tools/check_exercise.py 13`。校验日志自动保存，无需手工粘贴命令输出。自动检查未覆盖的真实集成仍需按本课项目标准验收。

### 开放表达与固定契约

最终回答允许中文、英文及不同句式，不要求出现closed、Lin等文本关键词。自动接口返回字典或带answer/reason/trace属性的对象；完成时answer为非空字符串，reason遵循completed/step_budget等约定。trace保留工具name、ok及成功value或失败error：开放工单查询lookup_ticket后查询lookup_owner，关闭工单只查询lookup_ticket；状态和负责人需来自输入。负责人缺失时轨迹必须保留ok=false，不通过检查回答中的某个词来猜测成功或失败。内部消息组织方式可自行设计；使用不同内部结构时请在solve_feedback入口转换为上述验收结构。自动检查不评价最终回答的自然语言含义。
