## 1. 信号量能替代令牌桶吗？

<details>
<summary>核对思路</summary>

不能。信号量限制同时在途数量，令牌桶限制可随时间恢复的消耗额度；短请求能在相同并发下产生很高的请求频率。

</details>

## 2. 为什么让测试传入now？

<details>
<summary>核对思路</summary>

可以精确构造同一时刻、补充后、时钟倒退等边界，不依赖真实调度或sleep的误差。

</details>

## 3. 本例平均39ms、p95为200ms矛盾吗？

<details>
<summary>核对思路</summary>

不矛盾。平均把所有时延加总再除以样本数；p95描述排序后的较慢位置，这里使用最近秩定义。

</details>

## 把规则放回一次执行

在[TokenBucket.allow](examples/demo.py)里记录每次调用前后：

| now / 请求 | 补充后tokens | 是否允许 | 扣除后tokens |
| --- | --- | --- | --- |
| 0 / 第1次 | 2 | True | 1 |
| 0 / 第2次 | 1 | True | 0 |
| 0 / 第3次 | 0 | False | 0 |
| 1 / 第4次 | 1 | True | 0 |

拒绝请求也会更新last，因为截至当前时间的补充已经结算；下次只能计算从这个时点以后新增加的额度。若不更新last，可能反复领取同一段时间的补充。

`ceil`从math导入，作用是向上取整。`[10] * 18`重复的是不可变整数值，得到18项列表；不要把这种安全性直接套到重复嵌套列表的情况。练习输出延迟指标时先说明样本与算法，再看是否满足预算，示例数据不代表真实系统性能。

## 验证范围提醒

给不同租户分别创建桶，只证明本进程内的额度隔离。多个进程各自拥有满桶会放大总额度；生产需要统一网关或原子共享存储。队列长度又是另一项约束，控制已经接收但尚未处理的等待量。
