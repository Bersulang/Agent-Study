## 3. 从问题建立机制

### 同时能做两件事，与每秒能接两件事不同

阶段06用信号量限制正在执行的查询数。若每个请求只用很短时间，即使并发为2，一秒内仍可发出很多次请求。供应商配额或企业成本约束可能要求限制时间窗口内的消耗，需要另一种模型。

本课使用令牌桶。capacity表示最多存多少额度，rate表示每秒补多少额度，tokens记录此刻剩余量。请求到来时先按经过的时间补充，再与capacity取较小值，最后判断能否支付本次cost。长时间空闲不能积累无限额度。

### 用手动时钟推导一次请求

容量2、补充速率1，时刻0初始tokens=2。第一次花1后剩1，第二次剩0，第三次额度不足返回False。它没有借贷额度，也没有睡眠等待。到时刻1，经过一秒补1，第四次请求就可以获准。

把时间作为参数而不是在测试中sleep，可以精确复现边界。now小于last意味着时钟倒退，函数拒绝；真实限流通常使用适合测间隔的单调时间，并明确多进程共享额度的问题。本例的对象在内存里，不是分布式配额服务。

### 平均延迟为什么藏得住慢请求

演示有20个延迟：18个10ms、一个200ms、一个400ms。平均是39ms，但仍有用户等了很久。percentile使用最近秩定义：排序后，取ceil(样本数×fraction)的那一项；列表从0开始，所以代码再减1。

p95的位置是ceil(20×0.95)=19，因此为200ms。不同统计库可能使用插值分位算法，必须先说明定义再比较指标，不能只比较两个都叫p95的数字。

Java线程池大小控制并发，令牌桶控制随时间补充的请求额度；两者可以同时使用。成本还应按租户与任务归集，不能让一个租户借用其他租户的预算而不被发现。

<details><summary>先预测：桶空后过了100秒，容量2、速率1会积累到100个令牌吗？</summary>

不会，补充后用min(capacity, ...)截断，最多为2。rate决定恢复速度，capacity决定可短时突发的上限，两者不能互换。
</details>

## 5. 跟踪一次完整执行

在[TokenBucket.allow](examples/demo.py)里记录每次调用前后：

| now / 请求 | 补充后tokens | 是否允许 | 扣除后tokens |
| --- | --- | --- | --- |
| 0 / 第1次 | 2 | True | 1 |
| 0 / 第2次 | 1 | True | 0 |
| 0 / 第3次 | 0 | False | 0 |
| 1 / 第4次 | 1 | True | 0 |

拒绝请求也会更新last，因为截至当前时间的补充已经结算；下次只能计算从这个时点以后新增加的额度。若不更新last，可能反复领取同一段时间的补充。

`ceil`从math导入，作用是向上取整。`[10] * 18`重复的是不可变整数值，得到18项列表；不要把这种安全性直接套到重复嵌套列表的情况。练习输出延迟指标时先说明样本与算法，再看是否满足预算，示例数据不代表真实系统性能。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 限流失效 | 各进程持有独立桶 | 生产用共享原子存储或网关限流 |
| 平均很快但用户抱怨 | 忽略p95和错误率 | 在目标负载下分层观察 |
| 降级导致越权 | 省略权限检查 | 安全约束不参与性能降级 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 9. 企业工程边界

给不同租户分别创建桶，只证明本进程内的额度隔离。多个进程各自拥有满桶会放大总额度；生产需要统一网关或原子共享存储。队列长度又是另一项约束，控制已经接收但尚未处理的等待量。

默认是单进程确定性容量教具，不代表真实负载性能。生产需并发安全、分布式原子计数、出口限流和供应商配额，并在真实模型延迟与目标负载下压测。

生产接入需要按场景明确身份、数据保留、故障恢复、容量和发布策略。本课程案例的验证范围是本地确定性行为，未调用真实外部模型或声称在生产环境通过。
