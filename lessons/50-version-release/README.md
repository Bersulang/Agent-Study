# 阶段 50：版本、发布门槛与回滚

## 1. 业务场景

只记录Git版本还不够。模型、提示词、工具Schema和知识索引都可能变，必须记录一次任务所用的完整配置，并防止质量回退。

## 2. 学习目标与前置知识

能建立完整版本包，推导坏发布不改active、旧任务不跟随active以及回滚不撤销数据的原因。

真正先修是Python基础、工具契约和状态/失败边界（对应阶段03—16）。本课不要求先完成30—38多Agent；可使用阶段39之后的服务或本地固定数据练习治理机制。按[项目里程碑](../../docs/milestones.md)持续把案例、权限、轨迹和发布记录合入主项目。

本课先根据固定输入推导正常与失败路径，再独立完成下方新需求；材料运行通过不表示已经掌握。

## 3. 从问题建立机制

### 同一份代码，为什么行为仍可能不同

把Git提交回退到昨天，助手仍可能回答不同：它调用的模型标识、提示词、工具Schema或知识索引没有回退。一次行为版本因此由五个部分共同描述，而不是只由代码提交决定。

示例bundle是一个字典，必须包含code、model、prompt、tool_schema、index五个非空字符串。fingerprint先验证字段，再把字典转成稳定JSON。sort_keys固定键顺序，separators去掉格式化空白；同一组字段内容不会因为字典构造顺序不同而产生不同摘要。

### 指纹能标识内容，不能证明内容正确

SHA256把稳定字节串变成摘要。只修改prompt版本也会改变摘要，方便将任务与完整配置对应起来。但有摘要不代表版本安全、质量合格或模型行为可精确重现；远端模型版本与随机性还需要供应商能力和运行证据支持。

这与Java部署时同时保存镜像、配置和数据库兼容信息类似。Git只覆盖其中一部分，不能替你锁定所有外部资源。

### 发布前检查，不能发布后补救检查

promote先得到候选指纹，再检查安全违规与成功率。只要有安全违规，或成功率低于0.9，就在修改registry之前抛错。通过后才把版本包保存进versions并更新active。这里0.9是固定教学门槛，真正门槛应按业务约定。

active是给新任务选择版本的别名。已经启动的任务保存具体版本ID，不能每个步骤重新读取active，否则一次长任务可能前半段用旧提示词、后半段用新工具Schema。

### 回滚改变入口，不倒放业务历史

rollback只允许切换到已登记版本。它不会删除新版本，也不会撤销已经创建的工单或逆转数据库迁移。示例的registry只在内存里，程序结束后丢失；真实系统要持久保存版本包、审计与兼容信息。灰度流量控制则是部署层工作，不在这个字典示例里实现。

<details><summary>先预测：候选版本成功率1.0，但security_violations非空，active会先改成新版本再回滚吗？</summary>

不会。检查发生在任何registry写入之前，直接抛ValueError，旧active从未改变。这样失败发布就不需要依赖第二个“补救写入”恢复现场。
</details>

## 5. 跟踪一次完整执行

按默认示例建立这张状态表：

| 动作 | versions | active | 已启动任务版本 |
| --- | --- | --- | --- |
| 首次发布v1配置 | 保存旧指纹与配置 | 指向旧指纹 | 尚未记录 |
| 启动任务 | 不变 | 不变 | 固定为旧指纹 |
| 提交含安全违规的prompt=v2 | 不变，候选未登记 | 不变 | 不变 |
| 对已登记版本调用rollback | 保留各版本 | 切换到指定指纹 | 不随别名更新 |

`{**bundle, "prompt": "v2"}`先展开旧字典条目，再覆盖prompt键，得到新的字典；旧bundle不变。promote里的dict(bundle)也复制外层配置，避免调用者随后改写原字典影响登记内容。字段只含字符串，所以这里的一层复制足以隔离本例修改。

源码与输出见[demo.py](examples/demo.py)。项目没有预置GitHub Actions目录；本地材料验证使用根目录tools/verify_course.py。未来接CI是可选集成，不应把不存在的配置当作已经运行的流水线。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 任务重启后行为变了 | 读取最新提示词而不是绑定版本 | 保存任务的完整版本包 |
| Git回滚仍错误 | 索引或Schema没有一起回滚 | 管理兼容的完整配置版本 |
| 安全回退仍发布 | 只看总成功率 | 安全失败设置硬门槛 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。

## 9. 企业工程边界

生产发布审查还要看工具权限范围、索引内容、数据库迁移兼容、回滚步骤与成本变化。版本指纹只帮助定位这些输入，不替代对它们的评估。

别名切换是内存教学机制，真实发布需要事务存储、兼容检查和流量控制；当前项目使用本地验证，没有预置.github流水线；接入真实托管平台后才有CI运行结果。

生产接入需要按场景明确身份、数据保留、故障恢复、容量和发布策略。本课程案例的验证范围是本地确定性行为，未调用真实外部模型或声称在生产环境通过。
