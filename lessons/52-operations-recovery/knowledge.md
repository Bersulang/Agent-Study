# 阶段 52 知识：备份恢复、事故与反馈闭环

[返回讲义](README.md) · [全局知识手册](../../docs/knowledge.md)

### 1. 恢复目标与演练

RPO是允许丢失多少近期数据，RTO是恢复服务允许花多久。明确目标后设计备份频率、恢复步骤和演练；有备份文件但没有恢复测试不足以证明可用。

### 2. 一致备份与完整性

数据库正在写入时直接复制文件可能不一致。SQLite backup API产生一致快照，恢复前执行integrity_check，恢复后检查关键业务数量与约束。

### 3. 反馈到评估的闭环

反馈先分类、脱敏、复核，再转为候选案例，验证修复后发布。用户反馈可能包含错误或攻击，不能直接覆盖生产规则。事故记录先恢复，再做根因分析与回归。

## 执行过程

初始化临时数据库并写一条任务；backup API产生快照；恢复函数检查备份完整性并复制到新库；读取确认数据；反馈去重后仅进入候选集合。所有演示在临时目录，不覆盖真实数据库。

## 新语法

`with sqlite3.connect(...)`只管理事务，不关闭连接；closing保证释放连接，组合with con保证提交事务；URI只读打开；executemany按参数组执行SQL。

## 判断与排错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 备份无法恢复 | 只验证文件存在 | 执行完整性检查和恢复后的业务查询 |
| 直接覆盖生产数据 | 恢复目标路径没有审核 | 先在隔离目录演练，确认后执行受控恢复 |
| 反馈污染规则 | 未经审核直接修改提示词 | 进入候选评估集，经标签和回归再发布 |

## 工程边界

本课是临时目录演练，不实施真实数据库恢复。生产还需加密、访问控制、异地备份、密钥恢复和数据库专用工具；SQLite教学结果不能等同Postgres灾备验证。

## 复习问题

实际恢复后读取数据而不是只看文件大小；解释RPO与RTO；说明反馈为什么先进入候选而非自动发布。

## Java联系与行为边界

Java try-with-resources会调用close；Python的SQLite连接上下文只负责事务，closing才负责关闭。备份前只读打开已有源，和Java中明确区分创建数据库与打开数据库的意图一致。

- source必须存在，否则FileNotFoundError且不创建文件。
- 源URI带mode=ro，防止connect静默新建库；target须不存在，保护原数据。
- backup API复制一致快照；restore先验证数据库格式，再验证tasks表及id/status列。
- 格式检查通过不等于业务完整，恢复后还要查数量、状态与约束。
- 所有连接退出前关闭，Windows临时目录才能安全清理。
