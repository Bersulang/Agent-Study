## 3. 从问题建立机制

### 修复一个加法错误，为什么要先记录旧内容

待修复文件calc.py把加法写成减法。看起来只需换一个符号，但在你审查补丁之后，文件可能又被别人改过。若仍把旧补丁直接写入，就可能覆盖新的合法修改。

patch因此先解析目标路径，要求父目录就是批准的root且文件名为calc.py，再读取原文，与批准时的BEFORE完全比较。这里严格文本相等是乐观并发的前置条件，不是要求开放题照抄表达；旧内容变了就拒绝，让人重新审查。

### 写入只是过程，测试结果才是修复证据

通过检查后写入固定AFTER，并用unified_diff生成可审阅差异。diff中的删除与增加行帮助检查改了哪里，但diff存在不代表行为正确。run_check随后启动独立进程，执行固定测试add(2,3)==5；改前失败、改后成功，才构成这个已知错误的回归证据。

一个测试仍不能证明所有加法场景都正确。独立练习需要依据新增需求选择反例，不能仅增加打印“通过”的代码。也不能因为助手声称修复完成就跳过实际运行。

### 子进程参数限制与操作系统隔离不是一回事

subprocess.run接收参数列表，避免把参数交给shell重新解释；cwd固定工作目录，timeout限制等待时长。`-I`隔离Python的部分环境与导入路径，但不禁止文件访问或网络访问。执行真正不可信代码还需要专门隔离环境，本例只执行自己编写的固定教学代码。

Java中ProcessBuilder也有参数、工作目录与超时管理，但创建子进程不等于创建安全沙箱。命令如何构造与进程拥有什么权限是两道问题。

### 只读报告也可能读错租户

report从预定义SQL模板中选count或by_status，再用问号参数绑定tenant。参数绑定保护数据值的解释，不会自动判断应该允许查询哪张表；模板白名单负责结构范围，WHERE tenant=?负责租户范围，query_only负责数据库连接的写入边界。

这三层不能互相替代。只读连接仍然可能读到全库，所以“没有UPDATE语句”并不代表访问范围正确。示例身份由调用方提供，生产中tenant必须来自认证身份，而不是信任用户随意传值。

## 5. 跟踪一次完整执行

默认演示创建临时calc.py和内存数据库，不修改项目源码：

1. 将BEFORE写进临时calc.py，运行固定断言。add(2,3)得到-1，因此子进程退出码非0，passed=False。
2. patch确认目标范围及旧内容，写入AFTER并生成差异。
3. 使用相同测试再运行一次，结果5满足断言，退出码0、passed=True。
4. 内存库中分别插入A/open与B/done，开启query_only，按tenant=A查询count，返回一行元组(1,)。

`splitlines(True)`按行分割且保留换行，使unified_diff能生成正常文本差异。`fetchall()`返回行序列，每行是元组，所以`[(1,)]`不是一个数字列表；元组末尾逗号表示只有一个元素。

源码见[demo.py](examples/demo.py)。独立练习中的报告适配器与实际写补丁、跑测试是两个层次：报告不能替代真正执行记录。

## 6. 常见错误与排查

| 症状 | 原因 | 排查与修复 |
| --- | --- | --- |
| 修复声明与实际不符 | 没有运行真实测试 | 在受限工作空间执行固定测试并检查退出码 |
| 参数列表仍不安全 | 调用对象是任意不可信脚本 | 区分避免shell注入和OS沙箱 |
| 只读查询泄漏租户 | 忽略查询WHERE范围 | 强制tenant与限定报告模板 |

排查时保留输入类别、状态与错误码；涉及身份、密钥和业务数据时，先脱敏再记录。一次运行成功只能证明当前案例，必须覆盖变化后的需求和失败路径。
